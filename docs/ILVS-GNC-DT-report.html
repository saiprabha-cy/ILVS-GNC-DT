01 — OVERVIEW

What this project is, and why it's scoped this way

Every real launch vehicle solves the same problem this project solves: fly a thrust- and mass-changing vehicle through a drag-bearing atmosphere, close a real-time guidance loop that has to reject disturbances, survive a discrete staging event, and hit a target insertion window — under the fixed-step, deterministic constraints of embedded flight hardware, not just inside a MATLAB script.

This project was deliberately rescoped from an original nine-phase, full-mission-lifecycle plan down to one thing done properly: the roughly 200 seconds between engines-light and payload-on-its-way-to-orbit. That's the one flight regime a five-repository sibling portfolio (satellite attitude control, attitude estimation, a CCSDS-style ground segment, embedded flight-computer telemetry, and autonomous ground navigation) didn't already cover — so it became this project's entire scope, rather than a ninth of a broader one.

03 — ENGINEERING APPROACH

How each subsystem works

Environment

A simplified exponential atmosphere (rho0 · e^(-h/H)) and inverse-square gravity (mu/(Re+h)²), non-rotating and spherically symmetric. Deliberately simple — the validation target is dynamic-pressure and drag estimates accurate to the regime that matters for this vehicle, not a full US Standard Atmosphere 1976 table.

Dynamics

A 7-state model: altitude, downrange, speed, flight-path angle, pitch attitude, pitch rate, mass. Translation and rotation are coupled only through angle of attack, kept deliberately separable so each could be validated independently — the translational-only equations reduce, with thrust and drag at zero, to pure central-force motion, letting specific mechanical energy conservation stand in as a direct correctness proof of the integrator and the gravity/flight-path-angle terms together.

Guidance & control

An open-loop pitch program (vertical rise → pitch-over kick → gravity-turn ramp) is tracked by a discrete PID with explicit, struct-based state — chosen specifically because that calling convention is what a hand-off to Embedded Coder expects, and because explicit state makes the controller unit-testable without anything hidden to reset between cases.

Staging

A discrete-event state machine, checked once per integration step rather than folded into the continuous equations — mass, thrust, and aerodynamic properties change instantaneously at separation, which is a different kind of software problem than "what are the forces right now," and is treated as one.

Embedded Coder

The closed-loop pitch guidance/control subsystem is built programmatically via the Simulink API, then compiled to portable C through Embedded Coder — proving the algorithm cross-compiles correctly, the same discipline already used elsewhere in this portfolio for attitude estimation, applied here to ascent guidance instead.

Telemetry

A thin packet format sharing its CRC-16 polynomial and packet philosophy with this portfolio's existing ground-segment project, deliberately — not a second, competing protocol.

05 — ENGINEERING LOG

Three real issues, found and fixed by real runs

Kept as an honest record rather than smoothed over — this is what actually happened between "the code is written" and "the code works."

ISSUE 01

Persistent state vs. continuous sample time

The PID block's persistent controller state can't inherit a continuous sample time from the blocks around it — Simulink refuses to compile it.

FIXED — a Zero-Order Hold inserted upstream forces the block's input to a discrete rate, which resolves its own sample time to discrete. Also the more physically honest model: a real controller samples a continuous plant through an ADC at a fixed rate.

ISSUE 02

A parameter that doesn't exist on every MATLAB version

The first fix attempt — setting SampleTime directly on the PID block — itself failed: that block resolves to a generic SubSystem object at the set_param level, which doesn't expose that parameter.

FIXED — replaced with the Zero-Order Hold approach above: a core block type with a reliably settable parameter, rather than chasing a version-specific name.

ISSUE 03

Continuous-time codegen disabled by default

With the sample-time issue resolved, rtwbuild failed differently: the ERT target disables continuous-time code generation by default, assuming a purely discrete embedded target — but this model's plant genuinely is continuous.

FIXED — SupportContinuousTime enabled explicitly. Codegen then succeeded completely, confirmed by a build log showing exactly two sample rates and two continuous states, matching the design intent precisely.
